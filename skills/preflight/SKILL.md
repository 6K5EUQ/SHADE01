# preflight — 비행 전 마지막 점검

```bash
./shade01 test          # 판정만 (기본)
./shade01 test -v       # 정상·참고 항목까지 전부
./shade01 test -t 10    # 텔레메트리를 10초 모은다 (기본 6초)
```

**실측 3~6초.** 종료코드로도 답한다 — `0` GO / `1` NO-GO / `2` 확인 후 판단.

🔴 **읽기 전용이다.** 보내는 것은 GCS 하트비트와 읽기 요청(`PARAM_REQUEST_READ`,
`MISSION_REQUEST_LIST`)뿐이다. `PARAM_SET`·`COMMAND_LONG`·미션 업로드를 **안 보낸다** —
FC 안의 값이 안 바뀌므로 `FC_CHANGELOG.md` 에 적을 일이 없다.

## 왜 이게 있나

같은 점검을 대화로 하면 왕복이 수십 번이다 — 파라미터 하나 읽고, 판정 묻고, 다음 것
읽고. 실제로 그 방식은 **수 분**이 걸렸다. 이 도구는 한 번 붙어서 한 패스에 끝낸다:
필요한 파라미터 **약 30개만** 골라 한꺼번에 요청하고(전량 1354개를 받지 않는다),
그 응답을 기다리는 **동안** 같은 소켓에서 텔레메트리를 주워 담고, 미션을 받아
이착륙 명령을 확인한 뒤, 판정표를 한 장 찍는다.

## 에이전트가 할 일

1. **`./shade01 test` 를 그냥 돌린다.** 파라미터를 하나씩 읽어 보지 마라 — 그게
   느렸던 이유다.
2. **출력을 그대로 보여주고** 그 위에 해석을 붙인다. 도구는 임계값만 알지 오늘의
   맥락을 모른다 — 어디서 날리는지, 바람이 어떤지, 무엇을 시험하려는지는 사람이 안다.
3. **NO-GO 가 나오면 그 항목만 파고든다.** 나머지를 다시 확인하지 마라.
4. **`기억할 것` 절은 판정과 무관하다.** 매번 같은 내용이라 "오늘 새로 생긴 문제"
   와 섞어 읽으면 안 된다.

## 붙지 못할 때 — 대개 이것이다

**FC 시리얼은 한 번에 하나만 쓴다.** 도구가 점유자를 이름으로 대 준다:

```
· /dev/ttyACM0 는 PID 1232455 가 쥐고 있다: python fcfetch.py get /fs/microsd/...
```

| 점유자 | 뜻 | 어떻게 |
|---|---|---|
| `mav_bridge.py` | 브리지가 돈다 | 그대로 두면 도구가 **UDP 로 알아서 우회**한다 |
| `fcfetch.py` | 로그를 내려받는 중 | 끝날 때까지 기다린다. **끊지 마라** — 남의 작업이다 |
| QGC | 지상국이 잡았다 | 사용자 창이면 물어보고 닫는다 |

연결 순서는 **시리얼 직결 → 브리지 UDP** 다. 시리얼이 비었으면 직결이 제일 빠르고,
브리지가 돌고 있으면 UDP 로 붙는다.

🔴 **`udpout` 은 우리가 먼저 말을 걸어야 한다.** 브리지가 보낸 쪽을 peer 로 등록한
뒤에야 하행을 준다 — 가만히 기다리면 영영 안 온다 (실측: 15초 무응답). 도구는
하트비트를 먼저 쏜다.

## 무엇을 보나

| 묶음 | 항목 |
|---|---|
| 🔴 쿼드 전용 잠금 | `RC_MAP_TRANS_SW=0` · `VT_ELEV_MC_LOCK=1` · **미션 이착륙이 22/21 인가** · 비행모드 6슬롯 |
| 🔴 failsafe | `NAV_RCL_ACT=2` · `NAV_DLL_ACT=2` · `RTL_*` 고도 · `RC_MAP_KILL_SW` 매핑 |
| 지오펜스 | `GF_*` — **꺼진 것이 정상이다** (켜져 있으면 그게 이상) |
| 전원 | 6S 전압·셀당 (21.0V 미만 NO-GO) · `BAT1_N_CELLS` |
| GPS·추정 | fix·위성·eph · EKF 혁신비 4종 · 센서 건강 비트 |
| 기체 | ARM 상태 · 지상 자세 · 진동 3축 · VTOL 상태 · RC 입력 · 홈 거리 |
| FC 자신의 말 | `STATUSTEXT` 경고 — `Preflight Fail: …` 는 NO-GO 로 올린다 |

### 🔴 미션 이착륙이 `22/21` 이어야 하는 이유

`84`(`VTOL_TAKEOFF`)는 이름과 달리 **"수직으로 떠서 → 고정익으로 전환하라"** 다.
`mission.cpp` 가 상승 후 `set_vtol_transition_item(FW)` 를 부른다 — **스위치를
거치지 않으므로 `RC_MAP_TRANS_SW=0` 으로도 못 막는다.** 미션 시동만으로 천이가 걸린다.

2026-09-04 기록은 "84/85 라서 진입 경로가 닫혔다" 고 적었으나 **정반대였다**
(`FC_CHANGELOG.md` 9/5 16:45 에서 규명). 쿼드 전용인 지금은 `22`/`21` 이 맞다.
고정익을 풀 때 — 에어스피드 영점을 잡은 **뒤에** — `84`/`85` 로 되돌린다.

## 판정이 모르는 것을 안전하다고 하지 않는다

하트비트를 못 읽었으면 `ARM 상태: 확인 불가` 로 **NO-GO** 다. "DISARMED" 라고
답하지 않는다 — 못 읽은 것과 무장이 안 된 것은 전혀 다르고, 전자를 후자로 답하면
도구가 모르는 것을 안전하다고 말하는 셈이다 (실제로 그 버그가 있었고 잡았다).

해석 못한 메시지가 있으면 개수와 종류를 `확인 필요` 에 적는다. 조용히 버리면
"왜 그 항목이 안 나왔지" 를 아무도 못 쫓는다.

## 기체 없이 시험하기

판정 코드 대부분은 **뭔가 잘못됐을 때** 도는 코드다. 멀쩡한 실기에서는 NO-GO
경로가 한 줄도 안 돌아 본 채로 남는다 — 정작 필요한 날에 처음 실행되는 코드가 된다.

```bash
# 터미널 A — FC 인 척한다
.venv/bin/python tools/preflight/fakefc.py good --port 14999
#   good  전부 정상 → GO
#   fw    미션 84/85 + RC_MAP_TRANS_SW=7 → 쿼드 전용 위반
#   nogps fix 1 · 3기      batt 20.4V      armed ARMED      vibe 진동 35 · EKF 1.4

# 터미널 B
./shade01 test -t 5 --conn udpout:127.0.0.1:14999
```

**화면을 고쳤으면 6개 프로필을 전부 돌려라.** `good` 만 GO 이고 나머지는 NO-GO
여야 한다. 이 시험이 실제로 세 가지 결함을 잡았다 — `hgt_ratio` 오타(EKF 항목이
통째로 빠졌다), 예외 하나가 점검 전체를 죽이던 것, 그리고 **ARMED 인데 GO 를
내던 것**(하트비트 파싱이 조용히 실패했는데 `armed` 없음을 DISARMED 로 읽었다).

## 임계값은 이 기체에 묶여 있다

`preflight.py` 상단 `EXPECT` 가 기대값·등급·근거를 한 곳에 모은다. 바꿀 때는
`FC_CHANGELOG.md` 의 근거를 같이 남겨라 — 값만 바꾸면 다음 사람이 왜인지 모른다.
다른 기체에 그대로 쓰면 안 된다.

## 도구가 못 하는 것 — 사람이 해야 한다

계기는 전선 안쪽을 못 본다. 이 기체는 **3m 낙하 이력**이 있고 **최대 90.2A**
(XT90 정격의 2배)를 뽑는다.

- **육안**: 프레임·모터 마운트·프롭 균열
- **손**: 착륙 후 커넥터 발열
- **arm 뒤**: QGC 지도에서 **H 아이콘이 기체 위**인지 — RTL 이 그리로 간다
- **조종기**: 모드 스위치 6단, `CH6 RC 캘리브레이션 금지` (슬롯 경계 여유 7us)
